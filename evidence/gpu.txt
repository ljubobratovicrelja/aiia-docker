# 1. One model download, two build targets (the shared `model` stage)
======================================================================
Both targets COPY --from the single shared `model` stage below, so the
1.28 GB GGUF is downloaded and sha256-verified once.  The second build is
the proof: its model stage is a cache hit, and only the COPY step of the
target differs.

--- docker compose build inference   ==> cpu target ---
#7 [model 1/2] FROM ghcr.io/ggml-org/llama.cpp:server
#7 DONE 0.0s
#8 [model 2/2] RUN mkdir -p /models  && curl -fL --retry 3 -o "/models/Qwen3.5-2B-Q4_K_M.gguf"         "https://huggingface.co/unsloth/Qwen3.5-2B-GGUF/resolve/f6d5376be1edb4d416d56da11e5397a961aca8ae/Qwen3.5-2B-Q4_K_M.gguf"  && echo "aaf42c8b7c3cab2bf3d69c355048d4a0ee9973d48f16c731c0520ee914699223  /models/Qwen3.5-2B-Q4_K_M.gguf" | sha256sum -c -
#8 CACHED
#9 [cpu 2/2] COPY --from=model /models /models
#9 CACHED

--- docker compose -f compose.yaml -f compose.gpu.yaml build inference   ==> gpu target ---
#8 [model 1/2] FROM ghcr.io/ggml-org/llama.cpp:server
#8 DONE 0.0s
#9 [gpu 1/2] FROM ghcr.io/ggml-org/llama.cpp:server-cuda13
#9 DONE 0.0s
#10 [model 2/2] RUN mkdir -p /models  && curl -fL --retry 3 -o "/models/Qwen3.5-2B-Q4_K_M.gguf"         "https://huggingface.co/unsloth/Qwen3.5-2B-GGUF/resolve/f6d5376be1edb4d416d56da11e5397a961aca8ae/Qwen3.5-2B-Q4_K_M.gguf"  && echo "aaf42c8b7c3cab2bf3d69c355048d4a0ee9973d48f16c731c0520ee914699223  /models/Qwen3.5-2B-Q4_K_M.gguf" | sha256sum -c -
#10 CACHED
#11 [gpu 2/2] COPY --from=model /models /models
#11 CACHED

Caveat, stated rather than hidden: on the GB10 the driver reports no
separate VRAM counters (memory total/used read N/A / 'Not Supported')
because the GPU shares the 128 GB unified memory pool with the CPU.  The
VRAM actually committed by the model is therefore read from llama.cpp's
own buffer accounting in section 6, and the pool size from --list-devices.

C. Reading the two stacks' RSS side by side (and one caveat)
======================================================================

  cpu stack, inference : 929 MiB under a gui-path load, 1.026 GiB when the
                         isolated API is hammered, against the 4 GiB limit
                         (22.7 % -> 25.7 %).
  cpu stack, gui       : 201 MiB against the 512 MiB limit (39.3 %), flat.
  gpu stack, inference : 767-807 MiB against the same 4 GiB limit (18.7-19.7 %).
  gpu stack, gui       : 201 MiB against 512 MiB (39.3 %) — same image, same
                         container, unchanged by the override.

  The GPU container's RSS is LOWER than the CPU container's although it is
  running the same model, because the weights live on the device: what stays
  in the container's memory is the host-side slice (llama.cpp reports a
  CPU_Mapped model buffer of 397.85 MiB for the mmap'd GGUF) plus runtime.

  CAVEAT worth stating, because it looks like an inconsistency:
  evidence/mint-3090ti-2026-10-24/gpu-device-and-offload.txt records
  '2.387GiB / 4GiB (59.67 %)' for the same container, captured by docker
  stats at a different moment.  Both are true.  docker stats reads the cgroup's
  memory.usage_in_bytes, which includes PAGE CACHE for the mmap'd GGUF; right
  after a build or a cold read the page cache for that 1.28 GB file is
  resident and counted, and it is evicted later.  So on this stack RSS is a
  range (0.77-2.39 GiB), not a constant, and the number to quote for 'what
  the container costs' is the under-load figure with the limit beside it,
  while the model's real footprint is the device number (1698 MiB per-process,
  see gpu-vram.txt), which docker stats does not see at all — the same split
  the gb10 artifact reported.

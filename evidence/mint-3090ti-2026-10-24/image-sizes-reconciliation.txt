WHY THIS FILE EXISTS

On the aarch64 host (gb10) `docker image inspect .Size` agreed with the sum of
the `docker history` SIZE column to within 1 MB, so evidence/image-sizes.txt
could decompose an image from its layers and the report could quote .Size as
'the image size'.  On mint (Engine 29.9.2) that agreement does not hold: .Size
comes out 23-42 % larger than the layer sum, on our images AND on the upstream
base images that nobody built here.  A report that quoted .Size on this machine
while the gb10 artifacts quote the layer sum would look like a 40 % regression
that never happened, so the four numbers are measured side by side:

  blob_bytes   Σ of the raw gzip layer blobs (what the content store holds) —
               this is the 'CONTENT SIZE' column of `docker images`.
  files_bytes  Σ of every regular file's size inside those layers, decompressed
               (the apparent footprint of the filesystem).
  history_sum  Σ of `docker history --no-trunc` SIZE — docker's per-layer
               accounting, which is what scripts/layer_analysis.py adds up.
  .Size        `docker image inspect --format {{.Size}}`, the number most tools
               and every report quotes as 'the image size'.

THE IDENTITY FOUND

  .Size  ==  history_sum  +  blob_bytes      (residual < 1 MB in all five images,
                                              which is the 3-significant-digit
                                              rounding of the history column)

i.e. on this engine .Size counts each layer's compressed size IN ADDITION to its
uncompressed size.  On gb10 it did not (CONTENT SIZE there read 0B, and .Size
matched history_sum).  The comparable number across the two hosts is
history_sum / files_bytes, not .Size.

======================================================================
CAVEAT, stated rather than hidden
======================================================================
* 'files_bytes' counts regular files only; directories, device nodes and
  symlinks contribute no bytes here, and whiteouts remove nothing from the
  number.  It is an apparent size, which is the thing a report means by
  'the image is 2.1 GB'.
* 'blob_bytes' is what the content store really holds, i.e. what the disk gives
  up.  That is the right number for a disk-space claim, and the wrong number
  for a 'how big is my image' claim.
* The layer counts differ between history (58 entries for the gpu image) and
  the manifest (15 layers): history lists metadata-only steps (ENV, WORKDIR,
  LABEL) as zero-byte entries, and its 3-significant-digit rounding is why the
  residual above is a few hundred kB rather than 0.
* The 'layer bookkeeping' residual in the two decompositions (a few MB, 0.2 % of
  the cpu image) is the difference between summing file bytes base-image + the
  copied GGUF and measuring the assembled image: a base layer stored as
  hardlinks or re-packed differs by that much.  It is smaller than the
  rounding of any figure the report quotes (0.1 GB), which is why the
  decomposition is presented as GB figures rather than bytes.

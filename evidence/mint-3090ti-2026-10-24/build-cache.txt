Read the classified view after each build:
  CACHED = buildkit reused the layer from the local cache and did NOT
           execute the instruction.
  RE-RAN = buildkit executed the instruction again.
For the model layer, CACHED is the difference between a 1.3 GB
re-download and nothing at all.

NOTE on `touch`: buildkit keys a COPY step on the content digest of the
copied files, not on their mtime.  A bare `touch` of app code therefore
leaves the image fully cached (B1).  What the Dockerfile ordering actually
buys is shown in B2, where the content changes: the pip layer survives,
the app layer does not.  Both cases are recorded here rather than
asserting the mtime story, which does not hold on this engine.

NOTE on re-running: the B2 marker line carries a unique timestamp and pid
on every run.  That is deliberate — a fixed marker string would itself be a
cache hit on the second run of this script and B2 would show CACHED for the
app layer too, i.e. the demonstration would stop demonstrating.  This was
found by re-running it.
